# Существующий ключ подписи

1.11 сохраняет production signing identity опубликованной `v1.10.47`. Скрипты принимают
**только существующий** `tgwatch-release.p12`, не генерируют или вращают ключ и не создают
новый открытый парольный файл. Установка с другим сертификатом не обновит старое приложение.

Ожидаемый SHA-256 сертификата опубликованной линии 1.7–1.10:

```text
AB74727A44F59684045E7DB4C820BE309F886433A18A3C06F3439417F3ACBEF1
```

Helper проверяет существующий alias `tgwatch` как приватную запись подписи и сравнивает
сертификат с ожидаемым до настройки Secrets. Configure также проверяет доступность
Secret-list API; ошибка readiness останавливает операцию до записи Keychain или Secret upload. Certificate-only запись, неверный пароль,
неожиданный сертификат и недоступный Keychain останавливают операцию. Для обычного выпуска
повторная настройка Secrets не нужна. Запуск настройки — отдельное действие владельца на
доверенном Mac с JDK 17+, авторизованным `gh` и доступом к нужному репозиторию.

## Защита прежней парольной копии

Если рядом с зашифрованным PKCS12 остался `tgwatch-signing-password.txt`, перенесите его
в macOS login Keychain:

```sh
python3 scripts/signing-keychain.py protect /secure/TgWatch-signing-backup \
  --expected-certificate AB74727A44F59684045E7DB4C820BE309F886433A18A3C06F3439417F3ACBEF1
```

Скрипт проверяет исходный ключ, сохраняет пароль в Keychain, читает его обратно и проверяет
восстановление того же сертификата в **отдельном процессе**. Только затем удаляет прежний
парольный файл. Ошибка любого шага оставляет его на месте; не удаляйте его вручную до
подтверждённого восстановления. Пароль не передаётся в аргументах команд и не выводится.

Проверка восстановления без печати пароля:

```sh
python3 scripts/signing-keychain.py verify /secure/TgWatch-signing-backup \
  --expected-certificate AB74727A44F59684045E7DB4C820BE309F886433A18A3C06F3439417F3ACBEF1
```

Настройка GitHub Actions Secrets существующим ключом:

```sh
bash scripts/configure-signing.sh /secure/TgWatch-signing-backup
```

Пароль берётся из login Keychain либо скрытого ввода терминала; значения передаются
`gh secret set` через stdin. В текущем workflow `init` и генерация нового ключа отсутствуют.
Эта документация не является разрешением менять Secrets или подтверждением такого изменения.

Храните резервную копию зашифрованного PKCS12 и login Keychain либо пароль в отдельном
доверенном менеджере паролей. Одного PKCS12 недостаточно. GitHub не позволяет прочитать
signing Secrets обратно. Полный путь PKCS12 входит в имя Keychain item; после переноса
каталога используйте исходный путь либо безопасно перенесите запись через Keychain Access.

Ранее ограниченная среда macOS возвращала `100001 / Operation not permitted` при записи
Keychain; прежний парольный файл тогда не переносился и не удалялся. Это историческое
ограничение среды, не новая проверка 1.11. Реальная операция требует доверенного Mac
владельца; Linux cloud не предоставляет macOS login Keychain.

В CI PKCS12 существует только во временном каталоге job и удаляется после сборки. Перед
публикацией предусмотрены сравнение production сертификата и обновление неизменяемого
`v1.10.47` APK. Его SHA-256:

```text
efd2147dae453c12288da5b3f33840f3dfb2f6b85032411f348fabb5e8e009d1
```

Локальный development-key upgrade проверяет данные и поведение, но не подтверждает
production-key continuity. Старая 1.6 с утраченной debug-подписью остаётся несовместимой.
