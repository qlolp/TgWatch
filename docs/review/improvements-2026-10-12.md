# TgWatch 1.13.1: сверка веток и следующие улучшения

Аудит исходного `main` `cf8da57a5da343f1055cb5d633ae31f2bfbd7676`
после PR #16–18. Проверены код, существующие тесты и отличия оставшихся веток.
Это исходные предложения по результатам чтения: во время этого аудита перечисленные
ниже сценарии ошибок не воспроизводились на телефоне или в новых regression-тестах.
Позднейшая реализация отмечена отдельно; описание исходных находок сохранено.

## Статус исправлений в 1.13.2

Подготовленная версия 1.13.2 / Android code 1013002 реализует четыре выбранных исправления:

- Пункт 1: несохранённый snapshot повторно записывается целиком перед возвратом к append.
  Атомарная замена синхронизирует родительский каталог; ошибка sync оставляет историю dirty.
- Пункт 2: `EXTRA` получил свой ограниченный трёхпоточный executor, отдельно от восьми
  потоков Telegram/control. Пулы принадлежат службе и закрываются при её завершении.
- Пункт 3 (поколение настроек): URL/enabled/generation и admission согласованы; completion
  принадлежит конкретному физическому запросу и не меняет delivery history нового адреса.
- Служебная отметка отката часов из раздела «Дополнительные границы данных» стала явной
  zero-width metadata; она сохраняет эпоху без ложной проверки в сводке или графике.

JSON payload новых копий имеет `formatVersion=2` и требует reader TgWatch 1.13.2+.
Внешний TGWB v2, шифрование и чтение старых поддерживаемых копий сохраняются.
[Описание версии и совместимость](../releases/1.13.2.md).

Пункт 4 (clipping переносимого backup), пункт 5 (network capabilities/pending requests)
и отдельный общий HTTP deadline вебхука остаются предложениями для следующих PR.
Этот раздел не заявляет публикацию APK или итоговый результат CI; его нужно сверять
по точному commit в GitHub Actions.

- Пять прежних Codex-веток уже являются предками `main`; их изменения сохраняются.
- Отчёт `cline/8j8mmkrk` включён как исторический аудит 1.12 с соответствующей
  пометкой. Исправления 1.13/1.13.1 не следует предлагать повторно по старым строкам.
- Основная реализация `codex/tgwatch-next-improvements` уже перенесена PR #16/18.
  Слияние сохраняет текущий `AppLocales` и явные JUnit assumptions: неподдерживаемые
  API 33 locale/API 30 inset-проверки считаются пропущенными, а не успешными.
- Две Cursor-ветки включены через merge-родителей с сохранением текущего дерева.
  Локализация, доступность, SemVer, дополнительная диагностика и вебхук уже
  реализованы в текущем коде. Старые START/STOP/provider API, классификация
  дополнительных сайтов как Telegram, CI-run-number версии и экспортированный
  boot receiver заменены принятыми реализациями.
- Glance, пишущая без чтения/retention/restore SQLite-копия и загрузчик того же
  списка пяти IPv4 DC остаются прототипами в истории. Причины отсрочки указаны
  в [плане развития](../development-roadmap.md). Их исходники доступны через
  merge-родителей; это не заявляется как внедрение этих подсистем.
- `claude/project-thread-s0ejzl` исключена из слияния и удаления.

Во время исходной сверки версия приложения оставалась 1.13.1 / Android code 1013001.
Производственный код при той сверке не менялся; обновлялись тестовые SDK-границы
и документация. Позднейшие изменения 1.13.2 перечислены выше.

## Предлагаемые следующие PR

### 1. Восстанавливать историю после временной ошибки записи

[History.kt](../../app/src/main/java/ru/tgwatch/History.kt), `record`, строки 94–107:
наблюдение добавляется в память до append, исключение записи только логируется.
После восстановления диска следующая проверка дописывает новую строку, но не
пропущенную. Завершение процесса до компактизации/штатного flush теряет эту
часть истории.

Добавить состояние несохранённой истории и повторять атомарную полную запись
перед возобновлением append. Проверка: сбой append → успешная следующая запись
→ перезагрузка хранилища сохраняет оба наблюдения. Приоритет P2, высокая
уверенность в пути кода; фактический сбой диска в этой итерации не моделировался.

### 2. Изолировать дополнительные проверки от пула Telegram

[NetworkProbe.kt](../../app/src/main/java/ru/tgwatch/NetworkProbe.kt), строки 110,
154,166,196: восемь Telegram-проб и `EXTRA` используют один восьмипоточный пул
с `SynchronousQueue`. Если DNS/transport дополнительного сайта не завершится
после отмены, следующий Telegram batch получит меньше workers и может пропустить
доступный DC. Исключение `EXTRA` из классификатора не устраняет этот путь влияния.

Дать дополнительным пробам отдельный ограниченный executor/deadline. Проверка:
зависшая дополнительная проба не сокращает выполнение следующего Telegram batch
и не меняет его статус. P2; существующие тесты проверяют изоляцию результатов,
но не конкуренцию дополнительных проб за workers.

### 3. Привязать вебхук и его gate к поколению настроек

[WebhookNotifier.kt](../../app/src/main/java/ru/tgwatch/WebhookNotifier.kt),
строки 38–43: URL читается до `gate.begin`. Если между ними пользователь сохранит
адрес B вместо A и сбросит gate, старый запрос A может отметить статус доставленным
в новом состоянии. Такой же статус затем не отправляется на B до следующего перехода.

Связать адрес, начало/завершение запроса и сброс с общим поколением настроек.
Добавить управляемый interleaving-тест. P2; последовательный reset уже тестируется,
конкурентная смена адреса — нет. Отдельно добавить общий monotonic deadline:
connect/read timeouts не ограничивают суммарное время slow-response/DNS запроса.

### 4. Сохранять корректность наблюдаемого времени при переносе бэкапа

[BackupManager.kt](../../app/src/main/java/ru/tgwatch/BackupManager.kt),
строки 30–45: snapshot использует неограниченный `History.snapshot(ctx)`.
Последний `until` может быть на 315 секунд позже `createdAt`; восстановление
через несколько минут сохраняет прогнозируемый хвост как наблюдённое время
переноса приложения.

Захватить один `now` для `createdAt` и использовать существующий
`History.snapshot(ctx, now)` при экспорте. Regression должен разделять
сохранение интервалов низкоуровневым restore и clipping переносимого экспорта.
P2; существующая fixture явно сохраняет будущий хвост и требует пересмотра
после согласования этой границы статистики.

### 5. Точнее реагировать на события сети и ручные запросы

[MonitorService.kt](../../app/src/main/java/ru/tgwatch/MonitorService.kt),
строки 242–245,445: каждое сообщение capabilities уже validated-сети увеличивает
revision. Изменение сигнала/скорости может превратить хороший текущий результат
в `UNKNOWN` и вызвать лишнюю проверку. Сравнивать identity сети и значимые
переходы validation/captive portal; повторение тех же capabilities не должно
инвалидировать результат. Частота такого поведения на устройствах не измерялась.

[CheckSchedule.kt](../../app/src/main/java/ru/tgwatch/CheckSchedule.kt),
`request`/`afterCheck`: запрос немедленной проверки во время текущей может быть
заменён обычным интервалом при завершении. Для ручного нажатия coalescing может
быть допустим, но новый набор настроек/extra probes должен получить проверку.
Явно определить pending-request политику и сериализацию, затем проверить
interleaving `request(0)` → `afterCheck`. Оба предложения P2.

## Дополнительные границы данных

- [Timeline.kt](../../app/src/main/java/ru/tgwatch/Timeline.kt), строки 52,122–131:
  rollback создаёт синтетический `UNKNOWN` marker, который позже включается в
  `checks`. Отделить epoch metadata от реальных наблюдений; проверить отсутствие
  ложной сводки «Checks:1» при остановленном мониторинге после отката часов.
- [HistoryStorage.kt](../../app/src/main/java/ru/tgwatch/HistoryStorage.kt),
  строки 78–82: fsync временного файла и atomic rename не синхронизируют каталог.
  Для гарантии после потери питания использовать уже имеющийся подход
  `RestoreTransaction.syncParent`; ошибка sync должна оставлять данные dirty.
