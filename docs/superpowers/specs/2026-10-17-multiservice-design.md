# C. Независимые цели мониторинга

Статус: проект для согласования. Зависимости: A и B из [общей спецификации](2026-10-17-growth-design.md).

## Модель и пользовательский сценарий

Одновременно существуют максимум четыре устойчивых идентификатора: telegram,
matrix, whatsapp, custom. Идентификатор не зависит от адреса, языка или подписи.
Пользователь включает цели отдельно и выбирает цель на главном экране. Каждая
имеет свои status, checkedAt, lastSuccess, history, coverage, incidents, правила
уведомлений и задержек. Общий экран не сводит их в один «Telegram недоступен».

Внутренний TargetStatus: OK, PARTIAL, DOWN, NO_NETWORK, UNKNOWN. Отсутствие
измерения находится в здоровье проверки и не является свежим UNKNOWN-наблюдением.
ProbeGroup продолжает обозначать вид свидетельства, а не сервис.

`TargetDefinition` описывает id/kind, включение, интервал и правила; приватный
endpoint читается отдельно. `TargetSnapshot` — неизменяемый результат с revision,
сетевым/настроечным generation и двумя шкалами времени. `TargetRepository`
предоставляет снимки и доступ к истории по id. `TargetRunner` выполняет одну цель;
общий scheduler не имеет отдельного Android Service для каждой из них.

## Что именно измеряется

| Цель | Свидетельство доступности | Ограничение |
| --- | --- | --- |
| Telegram | Текущие WEB и подтверждённый MTProto resPQ | Не доставка сообщений |
| Matrix | GET `/_matrix/client/versions`, HTTP 2xx и корректный JSON versions | Доступность указанного homeserver, не всей сети Matrix |
| WhatsApp | HTTPS `https://web.whatsapp.com/`, существующее правило HTTP reachability | Веб-инфраструктура; не аккаунт, звонки и медиа |
| Custom HTTPS | Выбранный публичный URL, HTTP 2xx | Проверка конкретного endpoint без авторизации |

Matrix по умолчанию предлагает matrix.org; смена homeserver проходит тот же HTTPS
validator, исключающий userinfo, query и fragment. Ответ Matrix читается с пределом
64 KiB; redirects не следуются. Для custom адреса — HTTPS, до 256 символов, без
userinfo/query/fragment, connect/read по 3 секунды, один HEAD и GET fallback
только при 405/501. Все операции под общим deadline, без отключения TLS checks.

Провал протокольной пробы даёт DOWN только при положительном контрольном
свидетельстве. Без него — UNKNOWN или NO_NETWORK по факту состояния сети.
Для одиночной HTTP-цели PARTIAL не придумывается. Подробность HTTP ошибки остаётся
локальной и обезличенной; payload не получает endpoint.

Telegram сохраняет интервалы и адаптацию текущей версии. Новые цели имеют интервал
60–300 секунд, по умолчанию 60 секунд. Ручная проверка проходит тот же admission;
частые нажатия не создают очередь. Будильник один, на ближайшую разрешённую цель.

Primary-бюджет Telegram из A остаётся отдельным. Три второстепенных физических
слота делят новые цели и EXTRA. Планировщик использует round-robin; физически
зависшая цель не захватывает повторно свои слоты. Каждая живая дополнительная
цель получает попытку в течение одного своего интервала при свободном бюджете.
Результат Telegram публикуется до ожидания остальных.

## История и миграция

Каждая цель получает отдельный журнал с прежней моделью Observation и epochs.
У Telegram максимум 65 000 строк, у каждой новой цели 11 000. Суммарно — 98 000.
Логическое окно семь дней; лимит строк может сократить фактическое покрытие при
частых ручных проверках, что явно отражается в B. Полная история всех целей не
загружается для отрисовки выбранной: активные снимки/агрегаты ограничены и кэшируются.

Новая файловая generation содержит registry и журналы по target id. Мигратор
копирует старую историю/настройки в telegram, проверяет их, делает fsync файлов и
каталогов, затем атомарно публикует manifest поколения. Старые файлы не удаляются
до подтверждённого завершения. Повтор после любого crash идемпотентен.

Существующие EXTRA-переключатели не включают новые самостоятельные цели при
обновлении. На экране предлагается явное преобразование с переносом настроек;
истории EXTRA в старом формате нет, поэтому прошлые измерения не изобретаются.
Если самостоятельная цель включена, эквивалентная EXTRA-проба не дублируется.

У каждой цели свои notification ids и переходы outage/recovery. Глобальные quiet
hours и mute по-прежнему действуют на все цели; дополнительные настройки не
обходят их. Новая цель по умолчанию выключена и не присылает first-run OK.

## Бэкап v3 и rollback

Криптография сохраняется: PBKDF2-HMAC-SHA256 600 000 итераций, AES-256-GCM,
случайные salt/nonce, полный tag проверяется до разбора и применения plaintext.
Новый JSON formatVersion=3 включает global settings, до четырёх target definitions
и observations с target id. Наблюдения допускаются в компактных tuples с точной
длиной и типами; произвольные поля/дубликаты ключей не принимаются.

Лимит plaintext v3 — 16 MiB, observations — 98 000, лог — прежние 150 строк по
4 096 символов. Контейнер допускает новый максимум плюс прежние 56 байт.
Декодирование v1/v2 сохраняет прежний лимит 8 MiB и 65 000 строк, преобразуя их в
telegram. Парсер v3 последовательно читает проверенный plaintext и не строит
полное дерево JSONObject поверх всей истории. Глубина JSON не превышает 10.

Credential URLs, automation tokens и webhook settings не экспортируются. После
restore мониторинг остановлен; дополнительные цели требуют проверки адреса и
явного включения. Старый EXTRA URL из v1/v2 переносится в приватную конфигурацию,
но не публикуется и не включает новую цель автоматически.

Restore всех журналов и настроек — одна transaction generation с durable pending
journal, а не независимые частичные замены. Неизвестный target id, дубликат id,
выход за лимиты или ошибка fsync отклоняют весь restore, сохраняя текущие данные.
Старые версии приложения v3 не понимают; перед downgrade нужен совместимый
Telegram-only export v2 с явной пометкой об исключении остальных целей.

## Совместимость и границы кода

`TargetDefinition`/`TargetSnapshot`/`TargetRegistry` отделены от Android lifecycle.
`TargetHistory` использует storage и timeline из A; Telegram History API остаётся
адаптером до перевода его потребителей. План должен явно охватить MainActivity,
MonitorService, boot, notification actions, widget, CSV, backup, diagnostic export.

Automation API v1 CHECK_NOW/GET_STATE без target id сохраняет Telegram и прежние
TG_DOWN-коды. Новые явные действия API v2 принимают allowlisted target id,
возвращают generic status и не разрешают менять endpoints или настройки.
Тот же bearer token, независимые разумные лимиты и общий физический admission.
JSON-вебхук B получает service_id выбранной включённой цели; gate, previous state
и cooldown разделены по цели, физический delivery slot остаётся один.

## Критерии приёмки

- Telegram DOWN при Matrix OK и обратный случай дают независимые графики/alerts.
- Долгий custom endpoint не откладывает Telegram и не накапливает потоки/очередь.
- Отключение/смена адреса цели отвергает старый результат и не меняет другую цель.
- Legacy v1/v2 history/backup и rollback epochs проходят round-trip без выдуманного
  покрытия; все crash-точки generation migration и restore проверены.
- Restore с ошибкой сохраняет старую целую generation и секреты установки.
- Максимальный допустимый v3 backup импортируется на worker в тестовом heap 128 MiB;
  превышения bytes/count/depth, malformed tuples, дубликаты и неизвестные id отклоняются.
- Direct Boot мониторит только встроенные цели без credential URL; приватная цель
  показывает «доступно после разблокировки», а не DOWN. После unlock стартует один раз.
- API v1, старый виджет и notification PendingIntents продолжают работать с Telegram.
