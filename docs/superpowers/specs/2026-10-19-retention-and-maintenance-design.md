# Долгая история и окна обслуживания: дизайн следующей итерации

Статус: предложение, не реализовано. Реализованные в этой итерации пункты —
[сверка 2026-10-19](../review/improvements-2026-10-19.md).

## Задача

Сейчас история ограничена семью днями и не знает плановой недоступности:

- `History.KEEP_MS` — семь дней, применяется в `prune`, `stats`, `incidents`, `exportCsv`
  и `prepare`; отдельной настройки хранения нет.
- Сырые проверки пишутся по одной строке на проверку (`History.record` → `TargetJournal`),
  потолки — `HistoryCompaction.MAX_DISK_ROWS = 66_024` и `MAX_DISK_BYTES = 16 МиБ`.
  При интервале 30 с неделя — это ~20 160 строк, поэтому 30 дней (86 400) и 90 дней
  (259 200) в текущие лимиты не помещаются.
- `CoverageStats` и `DayStats.unmonitoredMinutes` уже описывают ненаблюдённое время,
  а `Timeline`/`OutageEpisodes` не считают его доступностью. Плановое окно можно выразить
  этой же семантикой, не вводя новое понятие в статистику.
- `Prefs`/`TargetPreferences` не содержат ни ключей хранения, ни окон обслуживания;
  quiet hours только глушат оповещения и не исключают время из SLA.

## 1. Ярусная история

Цель: 7 дней сырых проверок (как сейчас), 30 дней минутных агрегатов, 90 дней
пятиминутных агрегатов, с явным выбором 7/30/90 в настройках. По умолчанию — сегодняшние
7 дней, миграция без потери данных.

Формат: новый журнал `history-v3.csv` на цель, строки-агрегаты
`epoch,bucketStartMs,resolutionMs,ok,fail,offline,partial,unknown,latencySum,latencyCount`
с `resolutionMs ∈ {60_000, 300_000}`. Сырые строки остаются текущего вида и читаются обоими
ридерами; понижение разрешения идёт от старых минут к новым.

Инварианты:

- Сумма `ok+fail+offline+partial+unknown` по агрегату равна числу исходных проверок;
  `latencySum/latencyCount` сохраняет среднее с насыщением (`LatencyTotal`).
- Агрегат никогда не пересекает границу эпохи часов и не «переписывает» наблюдения:
  rollup — только замена представления уже записанных строк.
- Потолки: 90 дней при 5-минутном разрешении — 25 920 строк на цель; 30 дней минутных —
  43 200. Бюджет памяти на цель — не больше 65 000 объектов `Observation`
  (`Timeline.retained`), бюджет файла — 16 МиБ, проверяется до записи.
- Запись остаётся durable-first: `HistoryStorage`/`TargetJournal` заменяют файл целиком
  только при смене разрешения и при ремонте, добавление — append с прежней политикой sync.

API (чистый Kotlin, тестируется без Android):

```kotlin
enum class Retention(val rawMs: Long, val minuteMs: Long, val coarseMs: Long) { WEEK, MONTH, QUARTER }
object HistoryRollup {
    fun rollup(rows: List<Observation>, now: Long, retention: Retention): List<Observation>
    fun bounds(retention: Retention): Bounds   // строки и байты до записи
}
```

`History` получает `retention(ctx)`, `prune` вызывает `rollup` вместо простого отсечения,
`stats`/`incidents`/`exportCsv` берут `days.coerceIn(1, retention.days())`.
В UI — выбор периода в существующем блоке истории; CSV-экспорт сохраняет текущую схему,
поэтому `CsvImport` не меняется.

Бэкап: TGWB v4 добавляет `retention` в снапшот настроек; v3-читатель остаётся, импорт
v4 в старую версию отклоняется по `schema`, а не молча теряет агрегаты. `BackupCodec`
и `TargetBackupCodec` проверяют лимиты строк до применения.

Тесты: rollup-инварианты (суммы, границы минут, эпохи; DST не участвует — время хранится
в UTC-мс), 90 дней в 16 МиБ, `targetBackupHeapTest` с максимальным v4-архивом,
миграция v2→v3 на фикстурах, восстановление после обрыва записи.

## 2. Окна обслуживания

Цель: плановая недоступность не создаёт инцидент, не портит uptime/MTTR и не шлёт
оповещения, но и не притворяется доступностью.

Модель (per-target, приватно, входит в переносимые настройки цели):

```kotlin
data class MaintenanceWindow(
    val id: String,            // стабильный идентификатор для идемпотентного restore
    val startMinuteOfDay: Int, // 0..1439, локальное время пользователя
    val endMinuteOfDay: Int,   // 0..1439, может быть меньше start — окно через полночь
    val daysMask: Int,         // битовая маска дней недели, 0 — каждый день
    val enabled: Boolean,
)
```

Проверка — чистая функция `MaintenanceSchedule.active(windows, localMinuteOfWeek)`.
Окно не материализует пропущенные проверки: во время окна цель не пишет строку истории,
поэтому интервал остаётся gap, а `CoverageStats`/`DayStats.unmonitoredMinutes` уже
считают его ненаблюдённым. Оповещения (`TargetAlertController`, `AlertRules`,
`SlowAlertController`) пропускают публикацию, но экран статуса продолжает показывать
живой результат.

Границы:

- Окно не отключает мониторинг и не останавливает службу: проверки продолжаются, чтобы
  после окна сразу был свежий статус.
- Переход в окно и из него не создаёт `DOWN`/`OK` эпизод: наблюдение просто не пишется.
- Восстановление бэкапа и смена часового пояса пересчитывают окно от локального времени;
  после rollback часов окно не «растягивается» — эпоха остаётся прежней.
- Пересечение с quiet hours допустимо: quiet hours глушит звук, окно исключает время
  из статистики и алертов.

UI: в диалоге цели — список окон (добавить/удалить/выключить), время выбирается теми же
пикерами, что quiet hours; строки локализуются в `values/` и `values-ru/`.

Тесты: `active` на границах минуты, через полночь, маска дней, DST-переход (локальное
время), отсутствие строк истории в окне, отсутствие алертов, сохранение живого статуса,
restore с тем же `id` не дублирует окна, clock rollback.

## Порядок и проверки

1. `HistoryRollup` + тесты без Android (отдельный коммит, поведение по умолчанию не меняется).
2. Настройка retention + UI + бэкап v4 (миграция и обратная совместимость).
3. `MaintenanceSchedule` + исключение из истории и алертов + UI.
4. Прогон `:app:testDebugUnitTest`, `targetBackupHeapTest`, instrumentation
   `BackupRestoreIntegrationTest`, `HistoryPersistenceIntegrationTest`,
   `TargetNotificationIntegrationTest`, `power-validation` на устройстве.

Риски: рост времени агрегаций на слабых устройствах (измерять на 30 и 90 днях до включения
по умолчанию), ошибки rollup на границе эпохи, забытые места с `KEEP_MS` (grep по константе
обязателен в ревью), двойной учёт после restore (идемпотентность по `id` и `bucketStartMs`).
