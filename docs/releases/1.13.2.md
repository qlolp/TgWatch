# 1.13.2 — history and request reliability

Source version `1.13.2`, deterministic Android code `1013002`, target API35.
This is a prepared release description; it does not claim APK publication or
F-Droid acceptance.

- After a temporary history append or replacement failure, the next successful
  write saves the full retained snapshot before appending again. Atomic
  replacement also synchronizes the parent directory; seven-day and 65,000-row
  bounds still apply.
- Informational EXTRA probes use three dedicated bounded workers, separate from
  the eight Telegram/control workers. A stuck extra transport cannot consume
  the next Telegram batch's worker capacity.
- Webhook admission validates an atomic URL/enabled/generation snapshot. An old
  request may finish after settings change, but its callback cannot change the
  new address's delivery history or release a different request. At most one
  physical request remains active across settings changes.
- A zero-width UNKNOWN record explicitly carries clock-epoch identity. It is
  excluded from check counts and the chart; real UNKNOWN observations, including
  a one-millisecond observation, remain checks. CSV's current seven-column
  format preserves this metadata without reviving archived epochs.

## Backup compatibility

New exports write JSON payload `formatVersion=2` inside the existing TGWB v2
encrypted envelope. AES-256-GCM and PBKDF2-HMAC-SHA256 (600,000 iterations) are
unchanged. The reader retains strict JSON payload v1 support, published binary
TGWB v1 support, and the previous local TGWBKUP1 format.

New copies require TgWatch 1.13.2 or later to restore; older app versions do not
understand JSON payload v2. No positive-width UNKNOWN record from an older
backup is reinterpreted as metadata. See [backup details](../backup.md).
